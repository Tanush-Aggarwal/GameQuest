# GameQuest — Decisions log

Record every design or architecture decision here so every AI tool follows the same choices.
Format: date — decision — why.

- 2026-10-26 — One LibraryEntry per user per game with an `ownerships[]` array — the product promise is a unified library; per-platform entries would duplicate games.
- 2026-10-26 — Progress kept as three separate tracks (manual, achievement %, playtime) — playtime is not completion; synced data must not overwrite user input.
- 2026-10-26 — Background jobs with Agenda on MongoDB instead of BullMQ — no Redis to host or pay for.
- 2026-10-26 — IGDB as main game data source (also unlocks Twitch clips with the same credentials); RAWG as fallback.
- 2026-10-26 — Discord: OAuth `identify` + validated pasted invite first; bot-created invites/events second — linking an account cannot create server invites.
- 2026-10-26 — Dark-first UI with Quest Violet accent and Loot Gold reserved for rewards.
- 2026-10-27 — Pixel-accurate visual fidelity recreation: warm ivory canvas (#F2EEE4), wide fantasy landscape hero backdrop with monolith and soft left-side ivory fade, 5 full-bleed trending game cards with dark bottom gradient and white title/rating overlay, Genshin Impact adventure card, character community banner, and removal of distracting ambient/panel background textures.
- 2026-10-26 — 3D features (Blender/VRoid) deferred until the full website is built.

## 2026-10-26 — Claude Code — item 3: auth design
- Access JWT (15 min) in HTTP-only cookie `gq_access` (path /); refresh JWT (7 d) in `gq_refresh` scoped to path /api/v1/auth. Prod cookies are Secure + SameSite=None, dev Lax.
- Refresh rotation: one RefreshToken doc per issued token (jti, familyId, usedAt, TTL on expiresAt). Used tokens are kept until expiry; replaying one deletes the whole family (reuse detection).
- Services take models by injection (`createAuthService({ User, RefreshToken, config })`) so tests run on in-memory fakes with no MongoDB. Real-DB behaviour (unique indexes, TTL) is not covered by tests yet.
- CSRF: no token yet. Mutations only accept JSON bodies (cross-site forms can't send them without a CORS preflight, which the CORS allow-list blocks). Revisit if non-JSON mutations are added.
- Register returns 409 naming the taken field (email/username). Accepted trade-off: it allows account enumeration, mitigated by the per-IP rate limit; revisit if email verification is added.
- Passwords are capped at 72 bytes in the shared schema because bcrypt silently truncates beyond that.
- A replayed refresh token within 10 s of its rotation returns 401 without revoking the family (two tabs refreshing at once); later replays revoke the whole family.
- If a DB error happens after a refresh token is claimed but before new ones are issued, the user must log in again (accepted).
- Logout deletes the refresh family; the access token stays valid until its 15 min expiry.
- Login does a dummy bcrypt compare for unknown emails to keep timing uniform.

## 2026-10-26 — Claude Code — item 5: game catalog
- The `Game` collection is itself the IGDB metadata cache (`cachedAt`, 30-day TTL, refreshed on view of a stale game). `MediaCache` is kept for trailers/clips/speedruns (Tier 2), not for core metadata.
- Cache-first search: MongoDB first; IGDB is queried only when a text search returns fewer rows than `limit` on page 1. A term is not re-sent to IGDB for 10 min (in-memory, per instance); a failed lookup is not remembered, so it retries.
- IGDB failures or missing Twitch credentials never fail `/games`: the response carries `warnings[]` (`UPSTREAM_ERROR` / `NOT_CONFIGURED`) and cached games. The adapter itself throws an `UpstreamError` naming the missing env vars.
- Game list sorts by `slug` with the slug as cursor (stable and cheap). Text-search relevance order is traded away; revisit with a score-based cursor if search quality matters.
- `slug` is `$setOnInsert` only, so public URLs never change when IGDB renames a game. Upserts use flat `$set` keys so other sources' `externalIds` and review counters are never overwritten.
- `/games` requires auth and has its own rate-limit bucket (300 / 15 min), because search can fan out to IGDB.
- Client: `useAsync` hook derives loading/error from the current load function so effects never set state synchronously (react-hooks lint rule) and stale responses are ignored. The Explore query lives in the URL (`?q=`).
- Server `dev` script uses `--watch-path=src` so OneDrive churn in node_modules cannot restart the server.

## 2026-10-26 — Claude Code — item 6: unified library
- Transitions (shared `LIBRARY_TRANSITIONS`, used by server and client): wishlist→backlog; backlog→playing|dropped|wishlist; playing→completed|dropped|backlog; completed→playing; dropped→backlog|playing. Includes the "undo" moves players really make (pause, resume, replay). Same-status and every other jump return 409 with `{from,to,allowed}`.
- New entries may only start as wishlist, backlog or playing (default backlog); Completed/Dropped are reached by moving, so the state machine cannot be bypassed on creation. Creation writes a StatusHistory row with `from: null`.
- Status change is a conditional update (`status: from` in the filter), so a double-click or second tab loses the race with a 409 instead of writing two history rows. No multi-document transaction: if the history write fails the status change stands and the error is logged.
- Completed sets `completedAt` and `manualProgress = 100`; leaving Completed clears `completedAt` and keeps progress.
- Entries are scoped by `userId` from the auth cookie in every query; someone else's entry is a 404, never a 403, so ids can't be probed.
- `GET /library` supports `?status=`, `?gameId=` (game page lookup) and cursor = last `_id` (newest first); tab counts are returned on the first page only. `PATCH /library/:id/visibility` is the dedicated hide-from-friends endpoint (no UI yet).
- `library.statusChanged` is emitted on an in-process event bus (`events/eventBus.js`); subscriber errors are caught and logged so they never fail a request. No subscribers yet (quests/activity come in Tier 4).
- Removing an entry also deletes its StatusHistory. The client confirms removal inline (Remove → Confirm/Cancel) rather than offering Undo.
- Server-test fakes: `createFakeCollection` in tests/helpers.js covers the Mongoose calls the services use; real indexes (unique pairs, sparse unique) are still not exercised against MongoDB.

## 2026-10-26 — Claude (cloud session) — deployment
- Production traffic goes browser → Vercel → (rewrite `/api/*`) → Render. The client calls `/api/v1` on its own origin, so auth cookies are first-party and use `SameSite=Lax; Secure`. Cross-site `SameSite=None` cookies are blocked in incognito/Safari, which is how evaluators open links. `COOKIE_SAMESITE=none` remains available for a direct cross-site setup.
- `TRUST_PROXY` is configurable (Render alone = 1, Vercel rewrite + Render = 2) so rate limits key on the real client IP.
- Real-time notifications use polling, not Socket.io: Vercel rewrites do not proxy WebSockets, and polling keeps the single-origin cookie model.
- Vercel builds from the repository root (`vercel.json`) so the `@gamequest/shared` workspace resolves; Render runs `npm ci` + `npm start` from the root for the same reason.

## 2026-10-27 — Claude Code — item 8: collections
- Manual collections store items in their own `CollectionItem` collection with a fractional `position`. A move writes the midpoint of the new neighbours (top: first-1, bottom: last+1); when two neighbours are closer than 1e-9 the list is renumbered 1..n once and the midpoint recomputed. Reorder is `PATCH /collections/:id/items/:itemId/position {afterItemId|null}` (dedicated endpoint, one write per move).
- Smart collections store nothing: rules are compiled on every read (`utils/smartRules.js`) from a whitelist of fields, operators and value types (shared `RULE_FIELDS` / `OPERATORS_BY_KIND`). Field and operator names are looked up with `Object.hasOwn`, values must be plain numbers/dates/strings (objects are rejected), so no user text becomes a Mongo key or operator. Rules are split by source: entry fields (status, manualProgress, lastPlayedAt) filter the owner's `LibraryEntry`, game fields (genres, platforms, timeToBeat.main, ratingAvg, releaseDate) filter `Game`; the owner's library bounds the query, never the catalog. A smart result is capped at 500 and pages by entry id.
- Items point at the owner's `LibraryEntry`, not at a `Game`, so status/progress show live and a collection can only hold games the owner has.
- Privacy is applied in `collectionService`: owner always; `public` for anyone not blocked; `friends` for friends; `private` owner only. A collection the viewer can't see is a 404 (existence is not revealed); a visible collection the viewer doesn't own gives 403 on writes. Entries marked `hiddenFromFriends` are removed from every non-owner view, including item counts and covers.
- The friend/block checks arrive through an injected `social = { isFriend, isBlocked }` (defaults: nobody is a friend) so collections don't depend on the friends feature; the friends item wires the real one.
- Ownership is enforced in the service (`loadOwned`) rather than a route middleware because it must pick 403 vs 404 from the collection's visibility.
- `library.entryRemoved` is emitted by `libraryService.remove`; `events/subscribers.js` listens and deletes the entry's collection items. The bus is now injectable into `createApp`.
- `collection.created` is emitted on create (for the activity feed later).
- Counts and covers in list views are computed per collection (2–3 queries each, page ≤ 24); acceptable at this scale, revisit with stored counts if lists grow.
- Seed: a real IGDB lookup overwrote Celeste's seeded 8h with 21.3h, so the "Short backlog" smart collection added two genuinely short backlog games (A Short Hike, Undertale).
- Small fixes made on the way: the LibraryEntry page used its own transition table (offered wishlist→playing, which the server rejects) and passed the wrong props to `ErrorState` (no Retry button); it now uses the shared `LIBRARY_TRANSITIONS` and correct props. Pre-existing lint errors (unused variables, unescaped quotes, setState-in-effect) were cleaned up.

## 2026-10-27 — Claude Code — item 9: friends + activity feed
- `Friendship` stores the pair sorted (`userA < userB` as strings) with a unique index, so there is exactly one document per pair whoever asks. Status is `pending | accepted`; declining or cancelling deletes the document (the sender may ask again), and crossed requests (A→B while B→A is pending) auto-accept. Dedicated endpoints: `POST /friends/requests`, `POST /friends/requests/:id/accept|decline`, `DELETE /friends/requests/:id` (cancel), `DELETE /friends/:userId`. Request creation has its own rate limit (30 / 15 min).
- Blocks (`Block {blockerId, blockedId}`) override everything: blocking deletes any friendship/request between the pair; a blocked player gets 404 on profile, search and requests (indistinguishable from "no such player"); the blocker gets 403 when trying to request ("unblock first"). `friendService` exposes `isFriend` / `isBlocked` / `friendIds` / `relation`, and collections + activity + profiles all use it, so there is one definition of "friend".
- Activity is written ONLY by event-bus subscribers (`events/subscribers.js` → `activityService.record`): `library.statusChanged`, `review.created`, `library.sessionLogged`, `collection.created` (and `session.created` for sessions). `reviewService` now emits `review.created` on a first review only (edits are quiet). Private collections leave no activity. The seed also builds alex's feed through the real services + subscribers, not by inserting rows.
- Visibility is stored as a coarse `level` (public/friends) and re-checked at READ time, because `hiddenFromFriends` and collection visibility can change after the fact: hidden entries drop out of everyone else's feed, library activity whose entry was removed is dropped, and a collection's activity follows its current visibility. Readers scan up to 5 batches to fill a page, and the cursor lets the client continue.
- Feed = friends' activity only (your own actions are not in it). Profile activity depends on the viewer: self sees all, a friend sees friends+public items, anyone else only public items (reviews and public collections).
- Profiles: `User.privacy` public | friends | private (default public), changed by `PATCH /users/me/privacy`. `GET /users/:username` returns `restricted: true` (no stats) for a viewer who may not see it, and the activity/collections endpoints answer 403; blocks answer 404. Stats leave out games hidden from friends. The three profile sections have separate endpoints so one failing section never blanks the page.
- Search is by username prefix on the lowercase copy, regex-escaped, ≥ 2 characters; users who blocked the searcher are excluded.
- Known gap: `/reviews/game/:id` and `/reviews/user/:userId` (from the reviews item) don't apply profile privacy or blocks; reviews are treated as public content for now.
- Test fakes: the auth fake's `User` is now a generic fake collection (24-hex ids, `find`, `$in`, `$regex`), so social tests can query the same users the auth service created.

## 2026-10-27 — Claude Code — item 10: game sessions
- `GameSession` stores `startsAt` and a derived `endsAt` (UTC), so "still upcoming" is one indexed comparison (`status = scheduled` and `endsAt > now`). A session in progress still counts as upcoming and still accepts RSVPs; once it has ended RSVPs close and the page says so. Cancelling is a soft delete (`status = cancelled`) so invitees see that it was cancelled instead of a 404; the calendar file then says `STATUS:CANCELLED`.
- Visibility: `friends` = visible to all of the host's friends; `invite` = only invitees (and the host). Anyone who can't see a session gets 404 (existence hidden); a viewer who can see it but isn't the host gets 403 on update/cancel. Blocks hide a session in both directions, even from an invitee. Invitees must be the host's friends.
- RSVP is its own endpoint (`PUT /sessions/:id/rsvp`), one answer per person (`Rsvp` unique on (sessionId, userId), replaced on re-answer). The host always counts as going; `maxPlayers` includes the host. Going is refused when full unless the person is already going, and the limit can't be lowered below the number already going. Capacity is checked before the upsert, so two simultaneous last-seat RSVPs could both succeed (accepted for now; a conditional update would close it).
- Discord invites are validated by pattern only — `discord.gg/<code>` or `discord.com/invite/<code>` (https/http/no scheme, optional `www.`) — and normalised to `https://discord.gg/<code>`; GameQuest never calls Discord. Look-alike hosts (`discord.gg.evil.example`, `evil.example/discord.gg/…`) and other schemes are rejected. Links render with `target=_blank rel="noopener noreferrer"` and only while the session is open.
- The `.ics` is built by hand (`utils/ics.js`): UTC `DTSTART/DTEND/DTSTAMP`, a stable `UID` (`<sessionId>@gamequest`), CRLF line endings, 75-octet folding that never splits a character, and text escaping so a title can't inject calendar properties. The client fetches it through the API (so the cookie is sent and errors become toasts) and triggers the download.
- Activity: `session.created` is recorded by the subscriber for `friends` sessions only (invite-only leaves no trace) and re-checked at read time, so a cancelled session disappears from the feed.
- Listing uses a composite cursor `"<startsAt ms>:<id>"` so sessions starting at the same moment page stably. The client groups by the viewer's local calendar day and always shows the viewer's timezone name.
- Editing: the form never re-sends an unchanged start time (minute precision), so a session already under way can still be edited; the server only rejects a *moved* start in the past.
- Zod `union` gave a generic "Invalid input" for a bad Discord link, so the optional-Discord fields use `preprocess` + `optional()/nullable()` and keep the real message. Cross-field refinements are skipped by Zod while another field has an error, so the form mirrors the invite rule to show every problem at once.
- Not built (out of scope here): reminder jobs 30 minutes before a session, Discord OAuth/bot, session clash warnings, recommend-a-game-to-a-friend-who-doesn't-own-it.

## 2026-10-27 — Claude Code — review fixes for items 8–10
- Session capacity is now atomic: `GameSession.goingCount` (people besides the host who answered Going) is incremented with one conditional update (`goingCount < maxPlayers − 1`, pinned to the `maxPlayers` that was read), and decremented when someone leaves Going. Lowering `maxPlayers` is a conditional write too (`goingCount ≤ newMax − 1`). Sessions created before the counter get it back-filled once from the real RSVPs. A concurrent-RSVP test covers it.
- Session access requires the viewer to still be the host's friend, even for invitees (an invitation doesn't outlive an unfriend); `listUpcoming` applies the same rule. RSVP rows from someone who is later unfriended are kept but hidden by the attendee rules below (known gap: they still count toward `going`).
- Attendee lists: nobody on either side of a block appears; the host sees everyone; invitees see each other; for an open (friends) session a guest who isn't the viewer's friend is only a number in the counts.
- Profile privacy gates a person's collections too: a private or friends-only profile makes its collections 404 for non-friends even by direct id (a missing owner counts as public). A collection's cover must be a game in the owner's own library that isn't hidden from friends.
- Ownership/role checks for collections and sessions live in the service (not a `requireOwnership` route middleware) because the right answer depends on visibility: 403 for someone who can see it, 404 for everyone else. The routes still require a session and validate every param/body with the shared schemas.
- `session.updated` / `.cancelled` / `.rsvp` are emitted but have no subscribers yet (they're for notifications later); the activity feed hides cancelled sessions at read time.

## 2026-10-27 — Claude Code — catalog import, DLC filtering and review fixes
- **What is a catalog game:** IGDB `game_type` in {0 main, 4 standalone expansion, 8 remake, 9 remaster, 10 expanded game, 11 port}, `version_parent` null, and a cover. The rule lives in one place (`isCatalogGame` in the IGDB adapter, ids in `shared/src/game.js`) and is applied in the bulk query, again on the returned rows, in live search, and by the import. Why: DLCs, bundles and editions polluted search results; filtering in the query and on the rows means a mocked or changed IGDB response can't leak them.
- **Hidden instead of deleted:** `catalog:fix` marks DLC/bundles/editions `hidden: true` with `parentGameId`. Library entries, reviews and sessions reference games by id, so deleting would orphan them. Hidden games are excluded from search/browse/recommendation sending; `withParentArt` shows the parent's cover/backdrop wherever a hidden game is still displayed (game page, library). A main game with no cover on IGDB is *not* hidden (type check only), it just gets the generated fallback cover.
- **Popularity:** one blended 0-100 score so games from different import steps sort together: log-scaled IGDB visits (0.35), want-to-play (0.25), Steam 24h peak players (0.25) and total rating count (0.15), each divided by the largest value seen. Metric ids are resolved by name from `popularity_types` at run time (IGDB's names are "Visits", "Want to Play", "24hr Peak Players"), never hard-coded. Catalog order is `popularity desc, slug asc`; the cursor is `<popularity>~<slug>` so paging stays stable. Games without a `popularity` field need `catalog:fix` (it backfills 0).
- **Import progress in MediaCache:** one document (`source: 'catalog-import'`, no `gameId`, expiry 5 years so the TTL index never removes it) holds the step, batch/offset and per-step counts. Upserts are by `externalIds.igdb`, so a resumed or repeated run never duplicates. Slug or Steam-id clashes on the unique indexes are retried (slug gets `-<igdbId>`, Steam id dropped) so one odd game can't abort the run.
- **IGDB limits:** requests are spaced 250 ms apart (4/s), pages are 500, and 429/502/503/504 retry up to 5 times honouring `Retry-After`, else exponential backoff (1s, 2s, 4s...). `external_games.category` is no longer returned by IGDB; the Steam id now comes from `external_game_source` (1 = Steam), with `category` still accepted.
- **Seed vs fix:** `npm run seed` no longer renames the slug of a game that already exists, otherwise it would undo the slug alignment done by `catalog:fix`.
- **Privacy:** `GET /games/:slug/friends` drops friends whose `User.privacy` is `private`, because the game page is another user's view of their library. `updateProfileSchema.avatar` accepts only `https://` URLs (or empty/null) so `javascript:`/`http:` URLs can't be stored.
- **Indexes in production:** `autoIndex` is off in production, so `npm run db:indexes` (`syncIndexes()` on every model) builds them; the seed runs it at the end and docs/DEPLOY.md lists it as a deploy step. Note `syncIndexes` also drops indexes that are no longer declared.
- **Line endings:** `.gitattributes` (`* text=auto eol=lf`) plus a one-off commit that stripped UTF-8 BOMs from 27 source files.
- **Seeded games had wrong IGDB ids (found after the first real run):** 20 of the 32 ids in `seed.js` pointed at unrelated IGDB games (Disco Elysium -> "Pacify", Balatro -> "Pegged", Baldur's Gate 3 -> Sekiro...). The import upserts by IGDB id, so it overwrote some seeded documents with those games, and the first `catalog:fix` aligned slugs, filled art/credits and hid two games (God of War Ragnarök, Dave the Diver) from the wrong games' data. Repair: `server/scripts/repair-seed-ids.js` (dry run by default, `--apply` writes) resolved each seeded title to its correct IGDB id, restored title/slug/cover, replaced the metadata and deleted the duplicate imported document only when nothing referenced it (library entries, reviews, collections, sessions, recommendations, play logs, activity, favourites). `seed.js` now carries the correct ids (its slugs are unchanged because the rest of the seed looks games up by them). Guard: `catalog:fix` compares the stored title with the IGDB name (word overlap >= 0.5) and leaves mismatching documents untouched, reporting them as suspects. Lesson: an id is only trustworthy if the title agrees with it.
- **Client covers:** `CoverImage` is the only way covers are rendered: IGDB `t_cover_big` / `t_cover_big_2x` via `srcset`, `loading="lazy"`, and a generated gradient (hue from the title) with the title when there is no art or the image fails. `compact` hides the title where one is already shown next to the thumbnail.

## 2026-10-27 — Claude Code — Phase 2: Steam link + sync, Steam art, trailers, Explore shelves
- **Linking:** SteamID64, `steamcommunity.com/profiles/<id>`, `/id/<vanity>` URL or bare vanity name (parsed in `shared/src/steam.js`; the text is only parsed, never fetched; a 17-digit number that is not a valid SteamID64 is rejected locally instead of being sent to Steam as a "vanity" name). A partial unique index on `User.steam.steamId` allows one GameQuest user per Steam account, so nobody can claim someone else's library. Unlinking removes the link and keeps the library entries and their Steam ownerships (the confirm text says so). Avatar and profile URL are stored only if https and on a Steam host. Vanity and player-summary lookups are not cached in `MediaCache`: they happen once per link attempt, behind a 10/15 min limiter (a conscious exception to "cache every adapter result").
- **Secrets:** the Steam and YouTube keys travel in query strings, so adapter errors are built from status codes only and never include the URL; tests assert the key is absent from errors and responses. A missing key gives the user a generic "not available right now" message, not a configuration hint.
- **Sync merge rules:** one `LibraryEntry` per (userId, gameId). Existing entries get only `ownerships` (Steam row replaced, other platforms kept), `achievements` and a forward-only `lastPlayedAt` (`$max`); their `status`, `manualProgress`, `loggedMinutes`, `completedAt` and StatusHistory are never touched, which is the safe reading of "never overwrite a status the user changed". New entries are `playing` if `playtime_2weeks > 0`, else `completed` if achievements are 100% (0/0 does not count), else `backlog`; playing wins over completed because the brief lists it first. Two Steam appids that map to one game (editions, regional SKUs) become one entry with summed playtime. A game Steam reports no achievements for (HTTP 400 "no stats") gets `unlocked/total: null`; a game whose achievements call fails keeps its previous snapshot and the run reports a warning (allSettled).
- **Events:** a sync does not emit `library.statusChanged` per new entry (hundreds of "added X" feed items and recommendation-outcome updates for a bulk import). It writes `StatusHistory` (`null -> status`) directly and emits one `sync.completed`; the activity subscriber records one "synced N games from Steam" item only when `added > 0`, so a re-sync that only refreshes playtime stays quiet.
- **Unmatched:** a Steam appid with no `Game.externalIds.steam` is looked up in IGDB `external_games` (source 1 = Steam). It is imported only if it passes the catalog rule (`isCatalogGame`); a game we already hold by IGDB id just gets the Steam id attached. Tools, soundtracks, DLC, editions and games IGDB does not know are returned in `unmatched[]` and never added. A hidden game (DLC kept for old library entries) matched by Steam id is reported as unmatched too. If the IGDB lookup fails, known games still sync and the rest are reported with a warning.
- **Known limits (sync):** the sync runs inside the HTTP request (as the brief asks) with an in-process per-user lock and an in-memory rate limiter. That is correct on one Render instance but not across instances or restarts, and a very large first sync can outlast a proxy timeout (the real 23-game run took 6 s; the achievement step is the long part). AGENTS.md prefers an Agenda job for long work: the follow-up is to return 202, run `syncUser` as a job and poll `user.steam.lastSync`. The limiter counts only successful syncs (`skipFailedRequests`) so a private profile can be fixed and retried at once.
- **Steam art:** `probeArt` HEADs `library_600x900_2x.jpg` / `library_hero.jpg` and `header.jpg` last (a landscape header used as a cover is cropped by `CoverImage`). Probing is cosmetic, so it uses a 5 s timeout and, after a failure, the art service leaves the CDN alone for 60 s; a failed probe is never cached as "no art". Results are cached in `MediaCache` (`steam-art`: 30 days for a hit, 7 for a miss) and written to `Game.cover/backdrop` only where empty, with a conditional update so IGDB art that arrives meanwhile is not overwritten. `toUpsertUpdate` no longer `$set`s a null cover/backdrop, because an IGDB refresh would otherwise wipe Steam-filled art. **Finding:** the 18 backdrop-less games have no Steam id (and IGDB has none for them either; they are obscure non-Steam titles), so `catalog:steam-art` fills 0 of them; they keep the cover-based hero.
- **Trailers:** IGDB `videos` first (the first valid id; IGDB videos are not always trailers). Otherwise one YouTube search per game per 7 days, cached in `MediaCache` (`youtube`), and "no result" is cached for 7 days too. A failed call is cached for 1 hour (slightly softer than "once per 7 days", so a transient error is not remembered for a week); a 403/429 pauses all searches for 24 hours because quota and key problems affect every game. An in-process memo plus in-flight sharing keep the guarantee when the database is stale or failing; without a key nothing is cached so adding one works at once. The iframe (`youtube-nocookie.com`) is created only on click; the thumbnail is an `i.ytimg.com` image, so YouTube's image host is contacted when the section renders (not the player).
- **Explore shelves:** each shelf is now a catalog query (`minRating`, `minHours`, `maxHours`, genre) returned in the API's popularity order, loaded in parallel with the main list and independently of it, each with its own skeleton / error+Retry; empty shelves are hidden. Before, the shelves filtered the first 24 games and re-sorted by the app's own `ratingAvg`, which is 0 for almost every imported game. Perf note: the filters use the `popularity` sort index and test documents one by one; a compound index or a short cache is the follow-up if the catalog grows a lot.

## 2026-10-27 — Claude Code — trailer quality: validated candidates, scoring, "Wrong trailer?"
- **Why:** the first version took IGDB's first video blindly (Witcher 3 showed "Developer Diary: Creating the Sound") and the top search hit (dubbed uploads, other games). Now every candidate is validated and ranked; see `server/src/services/trailerPicker.js` (pure, fixture-tested) and `trailerService.js`.
- **Candidates:** the game's IGDB videos (names kept in `Game.videoMeta` as a scoring hint; `trailers:refresh` backfills them) first; a YouTube search only when no IGDB candidate passes ("<title> official gameplay trailer", then "<title> official trailer" only if still nothing). Every candidate gets one `videos.list` check (50 ids per call, 1 unit). Without `YOUTUBE_API_KEY` nothing is shown at all, because an unvalidated video is never served (DEPLOY.md and README updated; this changes the old "optional key").
- **Strictness differs by source:** IGDB-listed videos are already attached to this game, so a tagline after the name is fine ("ELDEN RING – Rise, Tarnished | Official Launch Trailer"). Search results can belong to a neighbouring game, so they must (a) have only trailer/platform words before the name, and (b) after "Name – " have a first segment made only of trailer-tag words (so even a one-word subtitle such as "Silksong", "Alyx" or "Edgerunners" fails). That rejects "Bridge Constructor Portal", "Half-Life: Alyx", "League of Legends: Wild Rift", "Call of Duty: Modern Warfare 4", "Counter-Strike: Global Offensive", "Deus Ex: Human Revolution", "Mafia: The Old Country" and "Season 7 … | Arena Breakout: Infinite" for the base games (all found in the first live run over the 300 most popular games, then added as regression tests). The cost is a few false rejects of legitimate trailers with long taglines (e.g. "Assassin's Creed Brotherhood – Exotic Gameplay Trailer"); a missing trailer is better than a wrong one. Known limitation: a DLC trailer that IGDB itself lists on the base game is accepted unless its title says DLC/expansion; channel matching trusts the display name (anyone can call a channel "IGN").
- **Title rules:** the head of a subtitled title ("The Witcher 3" for "The Witcher 3: Wild Hunt") may stand alone only if it contains a number, or the rest is an edition label ("Minecraft: Java Edition"); otherwise "God of War" would accept the 2018 game for "God of War: Ragnarök". The rejection words and language words are looked for in the title without the game's own name, so "The Last of Us Part II" and "Top Spin 4" survive. A number is a sequel only when it directly follows the name ("Hades 2"); "Trailer 2", years, 4K and 60fps are fine. "I" never counts as a roman numeral; "V" and "X" count only when the game's own title ends with them (GTA V yes, "Xbox Series X" no). `und`/`zxx` (no speech) audio-language codes are not evidence of another language. A bare "gameplay" or "teaser" from a search needs "official" in the title or an official channel. Known limitation: a DLC named after the full title plus a short tag, with a separator, can still pass ("Elden Ring – Shadow of the Erdtree Gameplay Trailer"); explicit "DLC/expansion" words are rejected.
- **Scoring:** kind (gameplay trailer 50 > launch 40 > release 38 > reveal/announcement 35 > cinematic 32 > trailer 30 > gameplay 28 > teaser 24) + "official" 15 + developer/publisher or known official channel 25 + 5 x log10(views) + 5 for an IGDB-curated name. Channel matching is by brand, so "PlayStation Europe" and "Nintendo of America" count and "PlayStation Universe" or "Nintendo Life" do not. Observed effect: a very popular cinematic trailer can outrank a niche gameplay trailer (Witcher 3: "Killing Monsters" 73.4 vs "Debut Gameplay Trailer" 71.1). If gameplay trailers should win more often, lower the views weight; bump `CACHE_VERSION` afterwards so picks are recomputed.
- **Cache and quota:** `MediaCache` source `trailers`, payload `{ v: 2, pool: best 8, searched }`, 7 days (also when nothing passes); a failed lookup is kept 6 hours (not 1: a persistent search error would otherwise be retried 24 times a day per game); old v1 rows (source `youtube`) are ignored and removed by `trailers:refresh`. "At most one search per game per 7 days" now means one search round (query 1, then query 2 only if needed), not one `search.list` call. A 403/429 pauses all lookups for 24 hours, persisted in a `youtube-state` document (other instances see it within a minute) so a restart cannot spend more quota. Every search call is reserved atomically in that same document (an `$inc` that only matches while the day's count is under the ceiling of 90 = 9,000 of the 10,000 units), so API instances, restarts and the refresh script share ONE count; a first version counted per process and read-modify-wrote the total, which let an API server and the script together spend ~170 searches. The ceiling exists because the per-game guard alone let anyone with an account burn the quota by opening many uncached games; past it a game with no validated IGDB video shows nothing until the next UTC day and is not cached as "none". Process memos expire after 10 minutes so other instances' and scripts' writes are seen; an unreadable dismissal row is never remembered as "nothing dropped". A game whose second query was refused mid-way is cached as `partial` for 6 hours, not 7 days; a game refused outright is not cached but remembered for 10 minutes in memory so views do not repeat the work. Each evaluation logs `{ units, searches, listCalls }`.
- **"Wrong trailer?":** deliberately not "one click removes it for everyone" (which one account could use to empty any game: 20 reports an hour x 8 pool entries). A report hides the video for the reporter at once (their next list shows the next candidate); it is dropped for everyone once two different users reported it (`reportThreshold`), at most 10 drops per game, only videos in the game's current pool count, writes use `$addToSet`. The dropped id is excluded when the pick is next recomputed. Reports and drops expire after 90 days with their cache row (a drop is never permanent). The list is per user, so the GET and report responses are `Cache-Control: private, no-store`. Rate limit 20 an hour per user, confirm step in the UI. To undo a drop: delete the game's `trailer-dismissed` MediaCache row.
- **Embedding:** the iframe is created only on click, from youtube-nocookie.com with `hl=en&cc_lang_pref=en&cc_load_policy=0`, a `sandbox` (scripts, same-origin, presentation, popups; no top navigation) and a strict referrer policy. The thumbnail is an `i.ytimg.com` image fetched when the section renders.
- **First live run (`npm run trailers:refresh -- --limit=300`):** 300 games: 265 from IGDB, 31 from YouTube, 4 with nothing; 47 searches, 4,784 units. The 31 YouTube picks were then eyeballed; the neighbour-game false accepts above led to the stricter search rules, the cached entries were re-checked offline against them (46 entries dropped, 5 games cleared) and the cleared games plus Minecraft were looked up again (10 searches, 1,049 units). Final: 266 from IGDB, 28 from YouTube, 6 with no trailer (Fallout 1, Counter-Strike, Call of Duty, Mafia, and two obscure adult/joke titles). A last offline re-check against the final rules dropped 4 more entries and cleared 1 game (241 units to look it up again); the totals stayed 266 / 28 / 6. Total quota for the day about 6,200 of 10,000 units.

## 2026-10-27 - Claude Code - Google sign-in (ported from the old project)
- **Decision:** "Continue with Google" uses the server-side authorization-code flow: the API redirects to Google with a random `state` kept in a short-lived HTTP-only cookie, checks it on the callback, swaps the code for the profile (`adapters/auth/google.js`, plain fetch, no new dependency), then issues the same access and refresh cookies as a password login and redirects into the app. Failures redirect to `/login?error=<code>`.
- **Why server-side:** the client secret and tokens never reach the browser, and the cookies stay first-party like every other sign-in.
- **No linking by email:** if the verified Google email already belongs to a password account, sign-in is refused with a message to log in with the password. GameQuest does not verify emails, so linking could give an account to whoever registered the address first.
- **Data model:** `User.googleId` (partial unique index, like `steam.steamId`); `passwordHash` is required only when there is no `googleId`. Google-only accounts cannot use password login. Terms: the button carries a "by continuing you agree" notice instead of a checkbox, so Google sign-ups do not set `termsAcceptedAt`.
- **Setup is the owner's:** `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` go in `server/.env`; add `<origin>/api/v1/auth/google/callback` as an authorised redirect URI (docs/DEPLOY.md).
